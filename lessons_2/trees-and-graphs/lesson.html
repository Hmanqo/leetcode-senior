    Graphs and trees: one idea, different rules

    Dots, lines, and the rules that make some of them trees.

    Picture it

    A map of towns and roads. The towns are nodes (also called vertices), the roads are edges. Some roads are one-way (a directed graph), some have a length or a toll (a weighted graph). That's all a graph is: things, and which things connect to which.

    A tree is a graph with two extra promises: it's connected (you can get from anywhere to anywhere) and it has no loops. Together those mean there's exactly one route between any two nodes. Think of the folders on your computer: every folder sits inside exactly one parent, and you can't end up back where you started by only going into subfolders.

    Because a tree has no loops, you can walk it without remembering where you've been: going down can never bring you back to a node you've seen. A graph can loop, so every graph walk needs a visited set. That one difference explains most of what follows.

    The words you'll need

    WordMeaning
    rootThe top of a tree, the one node with no parent.
    leafA node with no children.
    depth of a nodeHow many edges from the root down to it. The root has depth 0.
    height of a treeThe depth of its deepest leaf. (LeetCode's "maximum depth" counts nodes instead, so it's height + 1.)
    subtreeA node plus everything below it. It's a complete tree in its own right.
    degreeIn a graph, how many edges touch a node. Directed graphs split this into in-degree (arrows in) and out-degree (arrows out).
    path, cycleA path is a route along edges. A cycle is a path that ends where it started.
    connected componentA group of nodes that can all reach each other, with no edge leading out of the group.
    DAGDirected Acyclic Graph: one-way edges, no cycles. Prerequisites, build steps, and (you'll see) every DP.
    The big idea

    A tree with n nodes always has exactly n − 1 edges: every node except the root has exactly one edge up to its parent. Add one more edge to a tree and you've made a cycle; remove one and it falls into two pieces. Problems like Redundant Connection and Graph Valid Tree are this fact and nothing else.

    A graph has 6 nodes and 6 edges and is connected. Is it a tree? think, then open

    No. A connected tree on 6 nodes has exactly 5 edges. With 6, there's one edge too many, so there's exactly one cycle somewhere.

    Why does the subtree fact matter so much? think, then open

    Because a problem about a tree can be answered by solving the same problem on two smaller trees (the left and right subtrees) and combining the answers. That's recursion, and it's chapter 3.

    02

    How a computer holds them

    Four ways to write a graph down, and which one LeetCode hands you.

    A drawing is for you. The computer needs the same information as data, and how it's stored decides what's cheap to ask.

    Node objects

    TreeNode(val, left, right)

    Each node knows only its own children, like a folder that knows its subfolders but not its parent. You get the root and nothing else. This is how LeetCode gives you trees.

    Adjacency list

    {A: [B, C], B: [A, D]}

    A phone's contact list: for each person, the people they can call. Cheap to list someone's neighbours. The default for graphs. Space O(V + E).

    Edge list

    [[0,1], [1,2], [2,0]]

    A list of roads. LeetCode usually gives graphs this way, and your first job is to turn it into an adjacency list. Union-Find and Kruskal like it as is.

    Matrix / grid

    grid[r][c]

    A mileage chart, or a chessboard. In a grid, nobody wrote the edges down: a cell's neighbours are computed (up, down, left, right). Chapter 8.

    Watch out

    An undirected edge [a, b] must go in both lists: adj[a].append(b) and adj[b].append(a). Forgetting the second is the most common graph bug there is. For a directed edge, add only one, and check which way the problem means it ("[a, b]: to take a you must first take b" points from b to a).

    Template: edge list → adjacency list Python
    from collections import defaultdict
adj = defaultdict(list)
for a, b in edges:
    adj[a].append(b)
    adj[b].append(a)      # leave this out if the graph is directed

    Recursion: delegate, don't micromanage

    The one mindset that solves most tree problems.

    Picture it

    The CEO wants to know how many people work at the company. She doesn't count them. She asks each of her direct reports, "how many people are in your part of the company, including you?" Each of them asks their reports the same question. An intern with no reports says "just me: 1." Answers flow back up, each manager adds their reports' answers plus one, and the CEO gets her number without ever looking past the people right below her.

    That is recursion on a tree, and the important part is what the CEO doesn't do: she doesn't think about the whole company. She trusts that each report will give a correct answer for their part, and she only decides how to combine those answers. Programmers call this trust the leap of faith. If you find yourself tracing the recursion five levels deep in your head, you've stopped trusting, and the problem gets harder, not easier.

    Three questions answer almost every tree problem

    1. What does a node report to its parent? Say it in one sentence: "the height of my subtree", "the sum of my subtree", "whether my subtree is balanced".
    2. What does an empty tree report? This is the base case: None returns 0, or True, or an empty list. Pick the value that makes the combine step work without special cases.
    3. How does a node combine its children's reports? "1 + the bigger of the two", "left + right + my value".

    Watch the answers flow up for "maximum depth". Notice that no node starts its answer until both children have finished theirs. That's what makes it a post-order problem: children first, then me.

    Two directions information can travel

    Bottom-up: reports

    return value

    Children report up, parents combine. Height, size, sum, balanced, diameter, LCA. The answer is returned. Most tree problems are this.

    Top-down: a backpack

    parameter

    A parent hands each child a backpack of facts about the route so far: the running sum, the depth, the allowed range. Path Sum, Good Nodes, validate BST. The answer is passed down.

    Many harder problems use both at once: a backpack going down (where am I, what have I seen) and a report coming up (what's below me). When you're stuck, ask: does this node need to know something about its ancestors (backpack) or about its descendants (report)?

    Cost

    Each node is visited once and does a fixed amount of work, so tree recursion is O(n) time. The paused calls waiting for answers take O(h) space, where h is the height: about log n for a bushy, balanced tree, but up to n for a tree that's really a long chain.

    Watch out

    Python stops recursion at about 1000 levels deep. A LeetCode tree shaped like a 10,000-node chain will crash with RecursionError. Either add sys.setrecursionlimit(10**5) or switch to an explicit stack (chapter 4).

    For "is this tree balanced?", what should each node report? think, then open

    Its height, with a special value (say −1) meaning "I'm already unbalanced somewhere below." A node checks: either child −1, or heights differ by more than 1? Report −1. Otherwise report 1 + the bigger height. Reporting just True/False doesn't work, because the parent also needs the heights to check itself.

    Count the "good" nodes: those with no ancestor larger than them. Backpack or report? think, then open

    Backpack: each node needs to know the largest value on the route from the root. Pass it down; a node is good if its value is at least that max. The count comes back up as a report. Both directions in one problem.

    Template: a bottom-up report Python
    def solve(node):
    if not node:
        return BASE                 # what an empty tree reports
    left = solve(node.left)         # trust it
    right = solve(node.right)       # trust it
    return combine(node.val, left, right)

    Three ways to walk around a tree, and one way across it

    Pre-order, in-order, post-order are one walk. Level order is a different one.

    People learn pre-, in- and post-order as three algorithms to memorise. They're really one walk with three moments when you could write a node down.

    So the only question is when a node does its own work, relative to its children:

    OrderNode's work happensUse it when
    ● Pre-orderbefore either childthe parent must act first: copy or serialise a tree, pass a backpack down, print a folder before its contents
    ● In-orderbetween left and rightthe tree is a BST: in-order visits values in sorted order (chapter 5)
    ● Post-orderafter both childrenthe node needs its children's answers: heights, sizes, deleting a tree, every "report" from chapter 3

    Step through each one on the same tree. Switch between the three with the buttons at the top, and watch the call stack: it's the list of ancestors that are paused, each waiting for you to return so they can carry on with their next job.

    The call stack is real

    When recursion "returns to the parent", the computer isn't searching for the parent. It kept a stack of paused calls the whole time. That's why any recursive tree walk can be rewritten with your own stack = []: you're just doing the computer's bookkeeping by hand. Pre-order is the easiest to write that way (push right child, then left, so left comes out first).

    Level order: floor by floor

    Picture it

    A building inspector who must finish every room on a floor before taking the stairs down. Depth-first walks follow one corridor all the way to the basement; level order sweeps across.

    A stack (last in, first out) gives depth-first. Swap it for a queue (first in, first out) and the same loop goes breadth-first: children added now wait behind everyone already in line, which is the rest of the current floor. The trick to know where one floor ends: count the queue before you start a floor. That count is exactly the floor's size.

    Level order answers anything about floors: right side view (last node of each floor), zigzag order, average per level, minimum depth (the first floor with a leaf), connecting each node to its right neighbour.

    Which order visits the root last? Which visits it first? think, then open

    Post-order visits the root last (everything else must finish first). Pre-order visits it first. In-order puts it between its left and right subtrees.

    Minimum depth: why is BFS better than DFS here? think, then open

    BFS goes floor by floor, so the first leaf it meets is the shallowest one, and it can stop right there. DFS might explore a very deep left subtree before discovering a leaf one step below the root.

    Template: level order Python
    from collections import deque
q, levels = deque([root] if root else []), []
while q:
    floor = []
    for _ in range(len(q)):          # exactly this floor
        node = q.popleft()
        floor.append(node.val)
        if node.left:  q.append(node.left)
        if node.right: q.append(node.right)
    levels.append(floor)

    Binary search trees: a sorted shelf, folded up

    One promise at every node, and what it buys you.

    Picture it

    "I'm thinking of a number between 1 and 100." You guess 50; I say "lower". Half the numbers just vanished. A binary search tree is that game, frozen into a shape: every node is a guess, left means "lower", right means "higher".

    The promise: at every node, everything in the left subtree is smaller and everything in the right subtree is bigger. Not just the children, everything. Searching means making one comparison per floor and throwing away the side that can't hold your value:

    Each step drops a whole subtree, so the cost is the tree's height: about log n if the tree is balanced, but n if it's a chain (insert 1, 2, 3, 4, 5 in order and you get a straight line). That's why real libraries use self-balancing trees; on LeetCode you're normally given the tree as it is.

    In-order is sorted

    Walk a BST in-order (left, me, right) and the values come out sorted. That's the shelf, unfolded. It turns many BST problems into list problems: the k-th smallest is the k-th node in-order; two numbers that add to a target are a two-pointer problem on the in-order list; a BST is valid exactly when its in-order walk is strictly increasing.

    Validating: every ancestor gets a vote

    The classic mistake

    Checking only "left child < me < right child" at each node. A node can satisfy its parent and still break the promise for its grandparent. Step through the broken tree below and watch which ancestor complains.

    The fix is a backpack (chapter 3): hand each node a window, the range its value must fall inside. Going left, the parent's value becomes the new ceiling; going right, it becomes the new floor. The window only ever shrinks, carrying every ancestor's rule along.

    The lowest common ancestor in a BST

    Start at the root. If both values are smaller, the answer is on the left; both bigger, on the right. The first node where they split (one on each side, or one equals the node) is the answer. It's the same search, looking for a fork instead of a value.

    In a BST, where is the smallest value? think, then open

    Keep going left until there is no left child. That node is the minimum. (Deleting a node with two children uses this: replace it with the smallest value in its right subtree.)

    Kth smallest: how can you stop early? think, then open

    Walk in-order with a counter, and stop the moment the counter reaches k. You never touch the larger values on the right.

    Template: validate with a window Python
    def valid(node, lo=float('-inf'), hi=float('inf')):
    if not node:
        return True
    if not lo < node.val < hi:
        return False
    return valid(node.left, lo, node.val) and valid(node.right, node.val, hi)

    06

    Answers that bend

    When what a node reports isn't the answer itself.

    In chapter 3 the root's report was the answer. The harder tree problems break that: the thing you report up is a piece of the answer, and the answer itself is recorded on the side as you go. Spotting this split is the step from easy to medium and hard.

    Diameter: return one arm, record two

    Picture it

    Lay the tree down like a set of pipes and ask for the longest single pipe run between two ends. Every such run has a highest joint where it bends: it comes up one branch and goes down another. At that joint, the run uses two arms. But if you want to extend the run further up the tree, you can only bring one arm with you, because a pipe can't fork.

    So each node does two different things: it records "left arm + right arm" as a candidate answer, and it reports "1 + the longer arm" to its parent. Watch the best path turn out to bend below the root:

    The same shape solves Binary Tree Maximum Path Sum (a famous hard): record val + left + right, report val + max(left, right), and treat a negative arm as 0 (you'd rather not take it). And Longest Univalue Path: an arm only counts if the child has the same value.

    Lowest common ancestor: two search parties

    Picture it

    Two people are lost somewhere in a company, and every manager asks their reports, "have you seen either of them?" The first manager who hears "yes" from two different directions is the lowest manager above both.

    Each node's report is one of three things: nothing, one of the targets, or the answer. Once the answer is found, it passes up unchanged, because every ancestor above it hears from only one side.

    Path sums: a backpack with a running total

    "Is there a root-to-leaf path adding up to t?" is a backpack problem: pass down t − node.val and check for 0 at a leaf. "Count paths that add to t, starting and ending anywhere going down" (Path Sum III) adds one idea from arrays: carry a count of the prefix sums on the current path. If the running sum is s and you've seen s − t above you k times, then k paths end here. Remove your prefix from the count as you return, because it's no longer above anyone. That clean-up on the way out is backtracking (chapter 12) appearing inside a tree problem.

    Building a tree from its traversals

    Pre-order always starts with the root. In-order has the root in the middle, with the whole left subtree before it and the whole right subtree after. So: take the first pre-order value as the root, find it in the in-order list (use a dictionary of positions so this is O(1)), and the number of values to its left tells you exactly how much of the pre-order list belongs to the left subtree. Recurse on both halves. Serialising a tree is the same idea backwards: write it out in pre-order with a marker for empty children, and read it back in the same order.

    Why can't the diameter function just return the diameter? think, then open

    Because the parent needs something else: the length of the single longest arm it could extend. A diameter that bends below a node is useless to that node's parent; you can't extend a path that already used both of its ends. So you return one thing and record the other.

    In Maximum Path Sum, why do we clamp arms at 0? think, then open

    An arm whose best sum is negative only makes the path worse. Taking 0 means "stop the path here and don't go down that side."

    Template: report one thing, record another Python
    best = 0
def arm(node):
    nonlocal best          # or self.best inside a class
    if not node:
        return 0
    L, R = arm(node.left), arm(node.right)
    best = max(best, L + R)        # record: the path that bends here
    return 1 + max(L, R)           # report: one arm only
arm(root)

    Exploring: chalk, string and ripples

    Depth-first and breadth-first search, and why they find different things.

    Walking a graph is walking a tree with one added danger: you can come back to where you've been, and walk in circles forever. The cure is a visited set, a chalk mark on every node you've reached. After that there are just two ways to decide where to go next.

    Depth-first: one explorer

    stack / recursion

    Theseus in the labyrinth with chalk and a ball of string. Go down any unmarked corridor, as deep as it goes. At a dead end, wind the string back to the last junction with a corridor you haven't tried.

    Breadth-first: a ripple

    queue

    A stone dropped in a pond, or a rumour where everyone tells their friends once per round. Everything 1 step away hears first, then everything 2 steps away. Nobody is reached before someone closer.

    Run both on the same graph and compare the green edges at the end. BFS leaves a bushy fan of short routes. DFS leaves one long snake.

    The one fact to remember

    BFS finds shortest paths when every edge costs the same, because the ripple reaches each node in the round equal to its distance. DFS doesn't: it reached H through a long detour. Use BFS for "fewest steps / moves / transformations". Use DFS when you only need to reach things or understand their structure: components, cycles, ordering, and every backtracking problem.

    Watch out

    In BFS, chalk a node when you add it to the queue, not when you take it out. If you wait until it comes out, the same node can be added many times by different neighbours before its turn, which can blow up the time and give wrong distances on some problems.

    Both visit every node once and look at every edge once (twice if undirected), so both cost O(V + E). To recover the actual route, not just its length, store "who found me" for each node as BFS goes; at the end, follow those pointers back from the target, like breadcrumbs.

    When the graph is hidden

    Often nobody hands you a graph. In Word Ladder, each word is a node and two words are connected if they differ by one letter. In Open the Lock, each 4-digit combination is a node, and turning one wheel one notch is an edge. The question "fewest moves from A to B" is BFS on a graph you generate as you go. Learning to see the graph in a puzzle is most of the skill.

    You need the shortest number of moves for a knight to reach a square. DFS or BFS? think, then open

    BFS. Squares are nodes, knight moves are edges, all edges cost 1. The round in which BFS first reaches the target is the answer.

    Clone Graph: why do you need a dictionary from old node to new node? think, then open

    It's the visited set and the result at once. When a neighbour is already cloned, you link to its clone instead of making a second copy, which also stops you looping forever around a cycle.

    Templates: BFS and DFS on an adjacency list Python
    from collections import deque

    Grids are graphs in disguise

    Flood fill, and many starting points at once.

    A 2-D grid is the most common graph on LeetCode, and it never looks like one. Every cell is a node. Its neighbours are the cells up, down, left and right (sometimes diagonals too), as long as they're inside the grid. You don't build an adjacency list; you compute neighbours on the spot with four direction pairs.

    Flood fill: the paint bucket

    Picture it

    The paint-bucket tool in a drawing program: click one pixel, and the colour spreads to every touching pixel of the same colour, and from those to theirs. To count islands, scan the map; each time you find land that isn't painted yet, that's a new island, so count it and pour the bucket there.

    The paint doubles as the visited mark: you can overwrite the grid itself (turn "1" into "0"), which saves a separate set. Ask first in an interview whether you're allowed to change the input.

    Many sources: drop all the stones at once

    "How far is each cell from the nearest X?" sounds like one BFS per X. It isn't. Put every X in the queue at the start, at distance 0, and run one BFS. The ripples spread together, and each cell is claimed by whichever ripple reaches it first, which is the nearest X. This is multi-source BFS.

    The same move solves Walls and Gates, 01 Matrix, As Far from Land as Possible, and Pacific Atlantic Water Flow (which also uses a second trick: search backwards, from the oceans uphill, instead of from every cell downhill).

    Watch out

    Check bounds before you read the cell: 0 <= r < rows and 0 <= c < cols. In Python, grid[-1] doesn't crash; it quietly reads the last row, and your flood fill wraps around the map.

    Surrounded Regions: capture every O region not touching the border. What's the trick? think, then open

    Reverse the question. Flood-fill from every O on the border and mark those as safe. Every O you didn't reach is surrounded; flip it. Starting from the border is much easier than checking each region for "does it escape?".

    Order and cycles

    Topological sort, and how to tell when an order is impossible.

    Picture it

    Getting dressed. Socks before shoes. Trousers before shoes and belt. Shirt before tie, tie before jacket. Some things don't care about each other: socks and shirt can go in either order. A topological order is any sequence of getting dressed that never puts on shoes before socks.

    These "must come before" arrows form a directed graph. An order exists exactly when the graph has no cycle: if A needs B, B needs C, and C needs A, nobody can go first. Course Schedule is this question in its purest form.

    Kahn's method: who's free to go?

    Count, for every item, how many arrows point into it: how many things it's still waiting for (its in-degree). Anything waiting for nothing can go now. Each time you place an item, cross out its outgoing arrows. Things it was blocking now wait for one fewer, and any that reach zero join the "ready" queue.

    The cycle test comes for free: if the queue runs dry before every item is placed, the leftovers are all waiting on each other. They're in (or stuck behind) a cycle.

    DFS with three colours: a trail of footprints

    The depth-first way to find a cycle needs one more idea than "visited". As you walk, leave footprints on your current trail. If you step onto a footprint, you've walked in a circle. When you back out of a node, wipe its footprint and mark it finished instead. Reaching a finished node isn't a cycle: it's just a second road into somewhere you've already fully explored.

    Bonus: if you write each node down at the moment it turns black (finished), and reverse that list, you get a topological order. Post-order again: a node is done only after everything that depends on it is done.

    Watch out

    Undirected graphs are different. There, every edge looks like a "loop back" to the node you just came from. To find a real cycle in an undirected graph, skip the edge back to your own parent, or use Union-Find (next chapter), which is simpler.

    Kahn placed 5 of 7 courses and the queue is empty. What does that tell you? think, then open

    The prerequisites contain a cycle, so the schedule is impossible. The 2 unplaced courses are in the cycle or depend on something in it.

    Alien Dictionary: you're given words sorted in an unknown alphabet. Where's the graph? think, then open

    Compare each pair of neighbouring words; the first position where they differ gives one edge, "this letter comes before that one". Topologically sort the letters. A cycle means the input is contradictory.

    Template: Kahn's topological sort Python

indeg = {u: 0 for u in nodes}

    Union-Find: clubs and presidents

    Answering "are these two connected?" while edges keep arriving.

    Picture it

    Everyone belongs to a club, and each club has a president. You don't know your president directly; you know your boss, who knows theirs, and so on up to someone who is their own boss. Two people are in the same club exactly when their chains end at the same president. Merging two clubs is one handshake: one president agrees to report to the other.

    BFS and DFS answer connectivity questions about a graph you already have. Union-Find (also called Disjoint Set Union) shines when edges arrive one at a time and you need to answer "connected yet?" after each. It has two operations:

    • find(x): follow bosses up to the president.
    • union(a, b): find both presidents; if they differ, make one report to the other.

    Two small habits make it nearly instant. Path compression: after a find, everyone on the chain is told the president directly, so next time it's one hop. Union by size: the smaller club joins the bigger one, so chains stay short.

    Reach for it when you see

    "Number of connected components / provinces", "does adding this edge create a cycle?" (union finds the same president: yes), accounts or emails that should be merged, "connect all points as cheaply as possible" (Kruskal, next chapter), and anything where edges are added over time.

    Redundant Connection: which edge makes a tree into a graph with a cycle? think, then open

    Union the edges one by one. The first edge whose two ends already have the same president connects two nodes that were already connected: that's the redundant one.

    Template: Union-Find Python
    parent = list(range(n))
size = [1] * n
def find(x):
    while parent[x] != x:
        parent[x] = parent[parent[x]]   # compress (halving)
        x = parent[x]
    return x
def union(a, b):
    ra, rb = find(a), find(b)
    if ra == rb:
        return False                  # already connected
    if size[ra] < size[rb]:
        ra, rb = rb, ra
    parent[rb] = ra
    size[ra] += size[rb]
    return True

    Roads with lengths

    Dijkstra, its cousins, and the cheapest way to connect everything.

    BFS finds shortest paths only when every edge costs the same. Give roads different lengths and the route with the fewest roads isn't the shortest any more. You need to always expand the closest unfinished place, not the oldest one in line. Swap the queue for a priority queue (a heap) and BFS becomes Dijkstra.

    Picture it

    Pour water into the pipe network at A. It spreads through every pipe at the same speed, so it reaches each junction by the shortest route, in order of distance. Dijkstra simulates the water: the next junction to get wet is always the closest dry one.

    Why is a settled distance final? When a place comes off the heap as the closest unsettled one, any other route to it would have to leave the settled area through some other unsettled place, which is already at least as far, and roads can only add length. That argument breaks if a road can have a negative length; then Dijkstra can be wrong, and you need Bellman-Ford.

    Lazy deletion

    Python's heap can't lower a value already inside it. So when a shorter route turns up, push a new ticket and leave the old one. When an old ticket comes out later, its place is already settled, so throw it away (the crossed-out tickets in the panel). Total cost: O(E log E).

    The family of shortest paths

    SituationUseCost
    All edges cost the sameBFSO(V + E)
    Edges cost 0 or 10-1 BFS: a deque, push 0-edges to the front and 1-edges to the backO(V + E)
    Non-negative weightsDijkstra (heap)O(E log V)
    Negative weights, or "at most k edges"Bellman-Ford: relax every edge, k (or V − 1) roundsO(k · E)
    Every pair of nodes, small VFloyd-Warshall: "can going through k make i → j shorter?" for every kO(V³)
    A DAGRelax edges in topological order (it's DP, chapter 14)O(V + E)

    Cheapest Flights Within K Stops is the classic trap: Dijkstra by price alone can throw away a route with fewer stops. Bellman-Ford with exactly k + 1 rounds counts stops naturally (copy the distances each round so one round can't use two new edges).

    "Minimum effort" or "lowest maximum height" problems are Dijkstra with a different idea of a route's cost: the largest step along it instead of the sum. Anything where extending a route can't make it cheaper works.

    Minimum spanning tree: building roads

    Picture it

    You must connect every town with roads, as cheaply as possible. Sort all possible roads by cost and build the cheapest first, but never build a road between two towns that are already connected; it would be wasted money (a cycle). Stop after n − 1 roads.

    That's Kruskal's algorithm, and "already connected?" is exactly Union-Find's question. Prim's algorithm grows one connected region instead, like Dijkstra, always adding the cheapest road leaving it. Both give the same total.

    Network Delay Time: a signal leaves node k. When has every node heard it? think, then open

    Run Dijkstra from k. The answer is the largest final distance, since the last node to hear it is the farthest one. If any node is still at infinity, return −1.

    Why does Dijkstra skip a ticket for an already-settled node instead of processing it? think, then open

    It's an older, worse ticket for a place whose shortest distance is already final. Processing it would only try longer routes onward, wasting time.

    Template: Dijkstra Python
    import heapq
dist = {src: 0}

    Backtracking: choose, explore, un-choose

    Depth-first search on a tree that only exists in your head.

    Picture it

    Trying on outfits for every combination of three items. Put on the hat. Now, with the hat on, try with and without the scarf. When you've seen everything with the hat, take the hat off before trying everything without it. Forget to take it off and every later outfit has a hat in it.

    Every backtracking problem builds an answer one decision at a time, and every sequence of decisions is a path in a decision tree. The tree is never stored. You walk it depth-first while holding just one path in your hands, and the walk follows three beats:

    1. Choose: make one decision (append to the path).
    2. Explore: recurse to make the rest of the decisions.
    3. Un-choose: undo the decision (pop) so the next option starts from the same state.
    Watch out

    When you record an answer, record a copy: out.append(path[:]). The path is one list that keeps changing. Append the list itself and every recorded answer will be the same list, which is empty by the end.

    Four shapes of decision tree

    Most backtracking problems are one of these. What changes is what a single decision is, and when a path counts as finished.

    FamilyOne decisionRecord whenSize
    Subsetstake or skip the next itemevery item decided2ⁿ
    Combinationspick an item at or after index start (so {1,2} and {2,1} aren't both made)path has k items, or hits the target sumC(n, k)
    Permutationspick any item not used yet (keep a used set)path has all n itemsn!
    Partitions / grid pathswhere to cut next, or which neighbour to step to (mark the cell, unmark on the way back)reached the end of the string / found the wordvaries

    Duplicates in the input (Subsets II, Combination Sum II, Permutations II): sort first, then at any one level of the tree, skip an item equal to the one just tried at that same level. Identical siblings would grow identical subtrees.

    Pruning: don't walk down a corridor you know is a dead end

    The decision tree is exponential, so the whole game is cutting branches early. Check a choice before recursing, and skip it if it can't possibly lead to an answer: the queen is attacked, the sum already went past the target, the word doesn't start with these letters. Each cut removes an entire subtree.

    Cost

    Backtracking time is roughly (nodes in the decision tree) × (work per node). Subsets: 2ⁿ · n. Permutations: n! · n. Constraints of n ≤ 10 to 20 on LeetCode are a strong hint that exponential backtracking is expected.

    Why do combinations use a start index but permutations use a used set? think, then open

    In combinations, order doesn't matter, so you only ever pick items after the last one you picked, which makes each set appear once, in increasing order. In permutations, order is the whole point, so any unused item can come next.

    Word Search: why must you unmark a cell when you return from it? think, then open

    The mark means "used on the current path". A different path, tried later, may legitimately pass through that cell. Leaving it marked would block it forever. Un-choose.

    Template: the backtracking skeleton Python
    out, path = [], []
def bt(start):
    if finished(path):
        out.append(path[:])        # a copy!
        return
    for i in range(start, len(nums)):
        if not allowed(i):         # prune
            continue
        path.append(nums[i])       # choose
        bt(i + 1)                  # explore
        path.pop()                 # un-choose
bt(0)

    Dynamic programming: backtracking with a memory

    When the decision tree keeps asking the same question.

    Backtracking explores every path because every path is a different answer. But many problems only want one number: the best, the cheapest, how many. Then two paths that reach the same situation have the same future, and working that future out twice is pure waste. Watch how often the plain recursion recomputes the same thing:

    Picture it

    A building full of rooms, each with a question on the door. To answer a door's question you need the answers from a couple of other doors. The first time you work one out, you stick a note with the answer on that door. Every later visitor reads the note instead of going inside. That's memoisation, and it's the whole trick.

    The state is a bookmark

    In a choose-your-own-adventure book, two readers who reach page 74 by different routes have exactly the same story ahead of them. The page number is all the book needs to know about the past. In DP, that bookmark is called the state: the smallest set of facts about "where you are" that decides everything still to come. Finding the state is the hard part of every DP problem. The rest is mechanical.

    Five questions that design any DP

    1. State: what does dp(i) or dp(i, j) mean, in one plain sentence? ("the fewest coins that make amount a", "the longest common subsequence of the first i letters of one word and the first j of the other").
    2. Choices: from this state, what can the last (or next) decision be?
    3. Recurrence: the answer in terms of smaller states, one per choice, combined with min, max or sum.
    4. Base cases: the smallest states, answered directly.
    5. Order: an order of filling in which every state's ingredients are already done.

    Top-down or bottom-up?

    Top-down (memo)

    @cache

    Write the plain recursion, then remember answers. Easy to get right, only visits states it needs. In Python, one decorator does it.

    Bottom-up (table)

    dp = [...]

    Fill a table from the smallest states up. No recursion limit, often lets you keep only the last row or two, so less memory.

    Same answers, same idea. A sensible habit: write it top-down first (it's the recurrence written out), convert to bottom-up only if recursion depth or memory becomes a problem.

    A table you can see: counting routes

    The DP families

    FamilyState usually looks likeExamples
    1-D sequencedp[i]: best answer for the first i items, or ending at item iClimbing Stairs, House Robber, Longest Increasing Subsequence, Word Break, Decode Ways
    Griddp[r][c]: best way to reach this cellUnique Paths, Minimum Path Sum, Maximal Square
    Two sequencesdp[i][j]: answer for prefixes of length i and jLongest Common Subsequence, Edit Distance, Interleaving String
    Knapsackdp[a]: best for a budget / target a, items considered one by oneCoin Change, Partition Equal Subset Sum, Target Sum
    Intervalsdp[l][r]: answer for the slice l..r, trying every split pointLongest Palindromic Subsequence, Burst Balloons
    Trees and DAGsa node's answer from its children's answersHouse Robber III, Longest Increasing Path in a Matrix (chapter 14)
    Bitmaskdp[mask][i]: which items are used so far, and where you areShortest Path Visiting All Nodes, small travelling salesman
    Coin Change: what's the state, and what's the choice? think, then open

    State: dp[a] = the fewest coins that make amount a. Choice: which coin is the last one used. So dp[a] = 1 + min(dp[a − c]) over every coin c ≤ a, with dp[0] = 0. Fill a from 0 upward.

    When is a problem DP and not backtracking? think, then open

    When it asks for one value (count, min, max, true/false) rather than every arrangement, and different paths of decisions reach the same state. If it asks you to list all the answers, you're backtracking; there's no shortcut around producing each one.

    Template: top-down with a cache Python

    if i >= n:                     # base case
        return 0
    take = nums[i] + dp(i + 2)     # one choice
    skip = dp(i + 1)               # the other
    return max(take, skip)
answer = dp(0)                     # House Robber

    DP on trees and graphs

    Where the two halves of this guide turn out to be one.

    Here's the idea that ties the whole guide together. Draw every DP state as a node, and draw an arrow from each state to the states it depends on. Because a state never depends on itself, there are no cycles: every DP is a DAG.

    Seen that way:

    • Bottom-up filling order is a topological order of the state graph (chapter 9).
    • Top-down memo is DFS on the state graph, with the sticky notes as the visited set (chapter 7).
    • "Minimum cost" DP is a shortest path in the state graph, and "maximum" is a longest path, which is easy only because the graph is a DAG.
    • If the state graph has cycles (you can return to a state), plain DP fails, and you need a graph algorithm instead: BFS for fewest moves, Dijkstra for cheapest.

    Tree DP: every node reports more than one number

    On a tree, the subtrees are the subproblems, and post-order is the filling order. The new trick: when a parent's options depend on a choice the child made, the child reports one answer per choice. In House Robber III, a parent can only be robbed if its children weren't, so each child reports both "best if I'm robbed" and "best if I'm skipped".

    The same pattern appears in Binary Tree Cameras (each node reports one of three states: has a camera, is covered, needs cover) and in the diameter and max path sum problems of chapter 6, which were tree DP all along.

    Memoised DFS on a grid

    Longest Increasing Path in a Matrix looks like a graph search with no obvious start. But an edge only goes from a smaller cell to a bigger one, so the cells form a DAG. dp(cell) = 1 + the best dp among bigger neighbours, memoised. Each cell is computed once, O(rows × cols), and no visited set is needed because you can never loop back to a smaller value.

    Bellman-Ford is DP too

    State: best[k][v] = cheapest way to reach v using at most k edges. Choice: the last edge used. That's why "within K stops" fits it so well: the number of stops is literally part of the state.

    Why does Longest Increasing Path need no visited set but Number of Islands does? think, then open

    Islands moves between equal cells (land to land), so it can walk in circles. Increasing Path only steps to strictly bigger values, so a cycle is impossible: the graph is a DAG, and the memo alone stops repeated work.

    Binary Tree Cameras: why can't each node just report "how many cameras below me"? think, then open

    The parent also needs to know whether its child has a camera (which covers the parent) or needs the parent to cover it. A count alone doesn't say. The state has to carry the choice, just like rob/skip.

    Which tool? Reading the problem

    The words in a problem statement that point to a technique.

    Half of a hard problem is noticing which chapter it belongs to. These cues aren't rules, but they're right far more often than not.

    "fewest steps / moves / transformations"

    BFS

    Equal-cost edges. If the graph is hidden (words, lock combinations, board states), generate neighbours on the fly.

    "distance to the nearest …"

    multi-source BFS

    Put every source in the queue at once.

    "cheapest / shortest" with weights

    Dijkstra

    Non-negative weights. A limit on stops or edges: Bellman-Ford.

    "prerequisites", "order", "dependencies"

    topological sort

    Kahn's in-degrees. "Possible at all?" means "is there a cycle?".

    "connected", "groups", "merge", edges added over time

    Union-Find

    Or one DFS/BFS per component if the graph is fixed.

    "count the regions / islands"

    flood fill

    Scan, and start a DFS or BFS at each unvisited cell.

    "all", "every", "list each" arrangement

    backtracking

    Choose, explore, un-choose. Small n (≤ 20) confirms it.

    "how many ways", "minimum", "maximum", "can you"

    DP

    If choices lead back to the same situation. Find the bookmark.

    tree: "path", "longest", "between any two nodes"

    report one, record one

    Diameter shape. Return an arm, record the bend.

    tree: depends on ancestors

    backpack (top-down)

    Pass the running sum, max, or valid range down.

    tree: "per level", "right side", "minimum depth"

    level order

    Count the queue before each floor.

    BST: "k-th", "sorted", "closest"

    in-order

    The shelf, unfolded. Or walk down discarding half.

    Constraints are a hint

    n ≤ 10: n! is fine (permutations). n ≤ 20: 2ⁿ is fine (subsets, bitmask DP). n ≤ 500: O(n³) is fine (interval DP, Floyd-Warshall). n ≤ 10⁴: O(n²) DP. n ≤ 10⁵ or more: O(n log n) or O(n), so BFS/DFS, Dijkstra, Union-Find, a single tree pass.
